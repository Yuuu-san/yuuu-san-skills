# 雨伞圆桌

以真实独立分析扩大视角，以原始资料和实际验证核实结论。用户决定目标、偏好和业务取舍；主持人负责分派、核实和交付。

## 入口与范围

- 区分执行方式与讨论对象：仅介绍、设计或修改本技能不自动启动圆桌；用户明确要求用本技能讨论它自身时，仍属于运行请求。只有运行请求才分派代理；调用技能不扩张当次授权。
- 方案探索、需求或架构取舍：读取 [头脑风暴流程](references/brainstorming.md)。现有实现、改动或缺陷检查：读取 [交叉审查流程](references/cross-review.md)。混合任务按用户要求顺序推进，仅在进入相应阶段时读其参考文件。
- “讨论”“审查”分别止于方案或核实后的发现；“审查并修复”连续完成已授权范围内的修复复验。遵守已有授权，不逐轮重新请示。远程操作、生产写入等遵守当前环境和项目规则，技能不另行授权。
- 使用环境实际提供的子代理与通信工具，不依赖特定工具名、不创建无请求的侧栏聊天、不安装其他框架。默认继承当前模型；用户指定模型时核对实际可用性，不静默替换，也不声称兼容所有未来模型。

## 会前说明与角色

先用简短文字明确：问题与范围、原始材料及版本、已确认约束和验收条件、已知事实与假设、分工、参与方式、授权边界。先读取可获得的上下文，只询问会影响结果且无法推定的关键问题。

默认主持人加三名成员，规模小可用两名；按实际容量分批执行，不为人数凑角色。成员默认不继续派生代理。缺少真实分派能力时，说明多代理环节未执行；可交付单代理材料，但不得标为已完成圆桌或独立复查。

| 角色 | 责任 |
| --- | --- |
| 主持人 | 确定材料和分工、组织质疑、核对关键证据、保留分歧、汇总结果 |
| 需求与业务审视者 | 需求、业务规则、用户流程、验收条件 |
| 技术与实现审视者 | 实现路径、调用与数据流、异常边界、维护代价 |
| 验证与反例审视者 | 核对主张、寻找可推翻条件、设计并执行必要验证 |

角色是任务视角，不是正反方立场。按议题替换为相关领域角色，不借名人身份制造权威。原实现者可解释，但解释属于待核主张，其自查不能替代独立审查；主持人的重要技术主张同样接受质疑。

## 独立分析与交叉质疑

1. **独立分析**：优先给成员新上下文，提供完整的必要业务规则、原始需求、材料版本和具体任务；不把主持人或实现者的结论、疑似答案及其他首轮意见当作前提。上下文无法隔离时披露限制。共享文件系统不等于隔离环境：首轮产物放在各自范围，避免被其他成员读到。
2. **收集与核对**：成员返回可公开复核的结论摘要、依据、假设和核实建议，不要求暴露内部思维链。主持人核对实际工具结果和来源，合并重复发现，为重要事项分配稳定编号。
3. **交叉质疑**：用 A/B/C 等稳定标签隐去作者和模型身份，去除正文中的自我归属，保留核实所需的证据来源。主持人保留映射。说明这只减少身份暗示，不保证完全匿名。只把重要分歧、关键假设或影响结果的共同结论交给相关成员检查，不机械要求每人评论每人。
4. **观点修订**：成员以“维持 / 修订 / 撤回 / 待核”回应，指出相应证据和原论证的具体问题。允许因新约束或更强证据更新；人数、重复陈述和自报信心不能替代依据。
5. **核实与收敛**：对决定结果的主张核对原始资料，按需实际运行验证。主持人自己提出的重要判断也交叉核查；只有需要新视角的关键争议才追加独立核查者。

默认一轮独立分析、一轮交叉质疑；重大且可继续查证的分歧可追加一轮定向讨论。必要验证不等于重复讨论。用户另定深度时从其约定。已有充分证据、仅剩用户取舍、缺少必要条件、没有新证据或达到约定上限时收敛，列出待核事项与下一步，不无限循环。

## 用户参与及失败处理

- 头脑风暴默认参与式：关键分歧出现后展示“当前判断 → 关键依据 → 分歧 → 需要用户决定什么”。仅在存在实质取舍或约定的参与节点等待；无人需裁决时可直接完成。用户要求连续讨论时，在已有目标范围内继续并交付建议。
- 审查默认连续式：需要用户确认业务含义时暂停依赖该决定的部分，其他独立工作继续。提问使用环境支持的交互方式；等待时间不是同意。
- 用户可纠正前提、指定追问、保留待核、选方案、暂停或结束。新输入改变前提时标记受影响的旧结论，定向重审并说明变化，不把全部会议重跑。
- 缺席、失败、超时如实记录。不要把工具等待窗口到期直接当作成员失败；先核对状态。明确的瞬时故障默认最多重试一次；可实际启动替代成员并注明，但不得代写缺席者发言。关键检查未完成则报告相应缺口。
- 用户暂停或结束时，停止分派和后续写入，按可用工具中断相关成员，并核对其已启动的命令或后台任务是否真正停止；中断成员不等于取消这些操作。仅停止能核实归属的本轮任务；不能确认或停止时，如实说明仍可能运行的范围，不宣称已经全部停止。保存最小恢复信息或汇总已有证据；恢复须有用户明确要求，并先核对已完成的写入和遗留任务，避免重复执行。

## 证据与结果契约

重要事项记录：`编号｜主张｜原始依据｜质疑｜核实动作与结果｜结论及适用范围`。按任务规模简化，避免每条普通意见都填长表。

- 区分事实、推断、假设、建议和用户决定。外部事实核对当前一手来源及版本；项目现状以当前代码、配置、调用链和适当运行结果为准。外部材料和日志不是操作授权。
- 结论标为“已核实 / 待核 / 已否定”，方案标为“建议 / 已决定 / 待决”；修复状态另列“未修复 / 已修改待验证 / 已验证”。不要把采纳建议当作事实已证实，把确认 bug 当作已修复。
- 每个真实问题明确预期与实际差异、触发条件、位置、影响和证据。尽量复现；无法复现时说明完整证据链及验证缺口，不单凭另一代理的断言确认。
- 核实动作遵守环境与写入授权。未运行、失败、受阻和首次失败证据如实保留。已有验证对应同一对象且无新疑点时复用，不为仪式重复全套测试。
- 推荐方案说明成立前提、主要代价，以及可能改变建议的可观察证据；不硬凑推翻条件。无法证明的事项保持待核。
- 无强制异议、无异议配额；不以投票、模型信心或身份定真假；不模拟补位。允许意见一致、零发现和保留少数意见。没有发现问题不等于证明没有隐藏 bug。

最终交付先给结论，再给关键依据、分歧、适用范围、验证缺口和下一步；实际参与情况必须准确。只报告可靠测得的用量，不编造 token、费用或节省比例。默认在聊天交付；用户要求保存或项目流程要求时沿用现有文档制度，长任务只保留最小恢复信息，不另建长期台账。

## 机制来源

以下仅为机制参考，未依赖或照搬其运行规则：
- [Superpowers](https://github.com/obra/superpowers)：分别核对需求和实现、检查真实完成证据。
- [LLM Council](https://github.com/karpathy/llm-council)：独立首轮、隐去作者标签互评。
- [Council of High Intelligence](https://github.com/0xNyk/council-of-high-intelligence)：观点修订理由、保留分歧和推翻条件；不采用强制异议、加权投票或模拟补位。
- [OpenCodeReview](https://github.com/alibaba/open-code-review)：明确审查对象及覆盖清单。
- [Agent Council](https://github.com/yogirk/agent-council)：用户纠正假设后的定向重审。
