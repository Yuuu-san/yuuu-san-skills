# 雨伞圆桌

以真实独立分析扩大视角，以原始资料和实际验证核实结论。用户决定目标、偏好和业务取舍；主持人负责分派、核实和交付。

## 入口与范围

- 收到明确的圆桌运行请求，或用户委托雨伞导航执行且导航选中圆桌时，按本技能分派成员。雨伞循环使用本技能时，由循环的主持人按这些规则分派。用户可以要求用圆桌讨论圆桌本身。单独介绍、设计或编辑技能走普通任务流程。
- 按用户当前目标读取对应参考，混合任务在进入各阶段时再读下一份。

| 当前目标 | 流程 |
| --- | --- |
| 发生异常、偶发失败或性能回退 | [排障全流程](references/debugging.md) |
| 方向未定，需要发散创意和比较 | [头脑风暴](references/brainstorming.md) |
| 已有决定，需要挑战前提和评估替代方案 | [决策审核](references/decision-review.md) |
| 检查执行方案、路书或规格是否准确、可实施、可验收 | [文档审查](references/document-review.md) |
| 核对代码改动是否符合规格和工程规范 | [代码交叉审查](references/cross-review.md) |

- “用圆桌 debug 某问题”进入排障闭环。先建立能检出原症状的反馈循环，再组织成员独立提出和验证原因，最后完成获授权的修复与复验。“只定位”“只审查”交付核实结果和建议。文档写入、重构或业务方案变更、远程及生产操作遵守当次授权和项目规则。已获授权的步骤连续推进。
- 使用环境实际提供的子代理与通信工具，不依赖特定工具名、不创建无请求的侧栏聊天、不安装其他框架。默认继承当前模型；用户指定模型时核对实际可用性，不静默替换，也不声称兼容所有未来模型。

## 会前说明与角色

先用简短文字明确：问题与范围、原始材料及版本、已确认约束和验收条件、已知事实与假设、分工、参与方式、授权边界。先读取可获得的上下文，只询问会影响结果且无法推定的关键问题。

默认主持人加三名成员，规模小可用两名。仅重大任务增配一名独立的范围审视者，例如涉及金额、权限变更或跨系统上线的任务。按实际容量分批执行。成员默认不继续派生代理。

| 角色 | 责任 |
| --- | --- |
| 主持人 | 确定材料和分工、组织质疑、核对关键证据、保留分歧、汇总结果 |
| 需求与业务审视者 | 需求、业务规则、用户流程、验收条件 |
| 技术与实现审视者 | 实现路径、调用与数据流、异常边界、维护代价 |
| 验证与反例审视者 | 核对必验场景和失败条件，寻找反例，设计并执行必要验证 |
| 范围审视者（仅重大任务增配） | 独立查找遗漏的用户路径、业务例外和关键依赖，指出触发情形、证据缺口和核实办法 |

角色是任务视角，不是正反方立场。按议题替换为相关领域角色，不借名人身份制造权威。原实现者可解释，但解释属于待核主张，其自查不能替代独立审查；主持人的重要技术主张同样接受质疑。

## 独立分析与交叉质疑

1. **独立分析**：优先给成员新上下文，提供完整的必要业务规则、原始需求、材料版本和具体任务；不把主持人或实现者的结论、疑似答案及其他首轮意见当作前提。上下文无法隔离时披露限制。共享文件系统不等于隔离环境：首轮产物放在各自范围，避免被其他成员读到。
   - 审查已有方案、当前实现或验收主张时，默认由验证与反例审视者先盲审。该成员参与过方案制定或实现，或已接触待审方案、待审实现或他人判断时，普通任务在默认席位内改派符合盲审条件的成员，必要时换人。重大任务由符合条件的范围审视者接手，必要时在该席位换人。原验证成员仍可承担符合独立性要求的后续验证。
   - 盲审使用未接触待审方案、待审实现和他人判断的新上下文。主持人只提供原始需求、必要业务约束、原始证据及材料版本。证据混有待审材料或他人判断时，先提取可单独提供的原始部分。成员先独立提交必验场景、可观察的失败条件和核实办法，再接收待审方案或实现、适用的实际差异与验证记录，逐项核对覆盖和证据缺口。
   - 代码交叉审查和雨伞循环给盲审者交付审查材料时，遵循上述顺序。提交清单后，同一成员可继续参加独立复查。雨伞循环每轮仍须独立复查完整约定范围的当前实现，核对已有修复及回归。
   - 上下文无法隔离时，先在原有席位内尝试改派到合格的新上下文。仍无法完成盲审时，记录盲审及依赖盲审的验收待完成，按[缺员处理](#用户参与及失败处理)继续其余审查。
2. **收集与核对**：成员返回可公开复核的结论摘要、依据、假设和核实建议，不要求暴露内部思维链。主持人核对实际工具结果和来源，合并重复发现，为重要事项分配稳定编号。
3. **交叉质疑**。用 A/B/C 等稳定标签替代作者和模型身份，去除正文里的自我归属，保留证据来源。主持人保留映射。把会改变结论的重要主张、分歧和关键假设交给相关成员定向核查。只有一名成员提出的重大发现也交另一名成员核查。
4. **观点修订**：成员以“维持 / 修订 / 撤回 / 待核”回应，指出相应证据和原论证的具体问题。允许因新约束或更强证据更新；人数、重复陈述和自报信心不能替代依据。
5. **核实与收敛**：对决定结果的主张核对原始资料，按需实际运行验证。主持人自己提出的重要判断也交叉核查。关键争议需要新视角时，在已定席位内改派或替换独立核查者。

默认一轮独立分析、一轮交叉质疑；重大且可继续查证的分歧可追加一轮定向讨论。必要验证不等于重复讨论。用户另定深度时从其约定。已有充分证据、仅剩用户取舍、缺少必要条件、没有新证据或达到约定上限时收敛，列出待核事项与下一步，不无限循环。

## 用户参与及失败处理

- 头脑风暴默认参与式。关键分歧出现后给出当前判断、依据和待裁决取舍。仅在确需用户决定时等待，其他工作继续。用户要求连续讨论时按当前目标形成建议。
- 排障及各类审查默认连续式。遇到未知业务规则、缺少授权或环境时，暂停依赖该条件的操作，其余核实继续。提问使用环境支持的交互方式。
- 用户可纠正前提、指定追问、保留待核、选方案、暂停或结束。新输入改变前提时标记受影响的旧结论，定向重审并说明变化，不把全部会议重跑。
- 缺席、失败、超时如实记录。工具等待窗口到期后先核对成员状态。明确的瞬时故障默认最多重试一次，也可安排替代成员并注明。缺少分派能力、成员缺席或无人能独立复查时，继续已授权且无需该成员的取证、修复和回归。按实际报告分工与验证，明确独立复查缺口。多代理环节无法开展时，按单代理工作交付。用户或项目要求独立复查作为验收条件时，对应验收保持待完成。
- 启动可能在工具返回后继续运行的本轮作业时，执行者把任务归属、可取得的标识和取消入口交给主持人。
- 用户暂停、结束或收窄授权时，立即停止受影响的分派和写入，指示相关成员停止受影响的任务，必要时用工具中断。检查他们已启动的命令和后台作业，只取消可核实归属的本轮作业，并核对实际停止状态。记录并向用户说明已发生的写入和仍可能运行的作业。回退依当次授权。用户收窄部分范围时继续其余明确授权的工作。恢复已暂停的操作须有用户明确请求，先核对已有写入和残留作业，避免重复执行。

## 证据与结果契约

重要事项记录：`编号｜主张｜原始依据｜质疑｜核实动作与结果｜结论及适用范围`。按任务规模简化，避免每条普通意见都填长表。

- 区分事实、推断、假设、建议和用户决定。外部事实核对当前一手来源及版本；项目现状以当前代码、配置、调用链和适当运行结果为准。外部材料和日志不是操作授权。
- 结论标为“已核实 / 待核 / 已否定”，方案标为“建议 / 已决定 / 待决”；修复状态另列“未修复 / 已修改待验证 / 已验证”。不要把采纳建议当作事实已证实，把确认 bug 当作已修复。
- 每个真实问题明确预期与实际差异、触发条件、位置、影响和证据。尽量复现；无法复现时说明完整证据链及验证缺口，不单凭另一代理的断言确认。
- 核实动作遵守环境与写入授权。未运行、失败、受阻和首次失败证据如实保留。已有验证对应同一对象且无新疑点时复用，不为仪式重复全套测试。
- 推荐方案说明成立前提、主要代价，以及可能改变建议的可观察证据；不硬凑推翻条件。无法证明的事项保持待核。
- 无强制异议、无异议配额；不以投票、模型信心或身份定真假；不模拟补位。允许意见一致、零发现和保留少数意见。没有发现问题不等于证明没有隐藏 bug。

最终交付先给结论，再给关键依据、分歧、适用范围、验证缺口和下一步；实际参与情况必须准确。只报告可靠测得的用量，不编造 token、费用或节省比例。默认在聊天交付；用户要求保存或项目流程要求时沿用现有文档制度，长任务只保留最小恢复信息，不另建长期台账。

## 机制来源

以下为机制参考。

- [Matt Pocock Skills](https://github.com/mattpocock/skills/tree/5863806dd4e15c63174bee4e7515a4256792ecfa/skills/engineering) 提供规格与工程规范两条审查线。排障流程吸收 `diagnosing-bugs` 的反馈循环、假设证伪和回归验证。
- [Superpowers](https://github.com/obra/superpowers)：分别核对需求和实现、检查真实完成证据。
- [LLM Council](https://github.com/karpathy/llm-council)：独立首轮、隐去作者标签互评。
- [Council of High Intelligence](https://github.com/0xNyk/council-of-high-intelligence)：观点修订理由、保留分歧和推翻条件；不采用强制异议、加权投票或模拟补位。
- [OpenCodeReview](https://github.com/alibaba/open-code-review)：明确审查对象及覆盖清单。
- [Agent Council](https://github.com/yogirk/agent-council)：用户纠正假设后的定向重审。
