# 排障全流程

## 1. 固定症状，建立反馈循环

- 主持人对齐用户可观察的预期、实际现象和验收条件，记录代码版本及相关本地改动、环境、入口和输入。查相关术语表（`GLOSSARY.md`）和架构决定（ADR），用来确认业务语义与真实调用路径。运行会干扰现有工作时，在隔离副本保留复现所需改动，核对候选的差异、连接目标及写入副作用。
- 首轮可让成员独立找复现入口、原始证据和可观察指标。主持人负责选定并实跑一个可反复执行的检查。优先复用项目测试，其次选能覆盖真实触发链的 CLI、接口、UI 自动化、日志回放或最小脚本。共享设备、端口或可变数据上的操作顺序执行。
- 把用户的**具体症状**写成可判定条件，例如错误码、输出像素或指定指标的退化。记录实际运行过的命令或操作、输入和判定结果。尽量缩短运行时间，固定时间、随机种子和可变状态，优先让执行者能自行重复。必须人工操作时，给出最少步骤、判定条件和证据采集方式。
- 分享命令、日志、截图或回放样本前，将凭证及敏感字段替换成 `<REDACTED>`。凭证通过环境变量读取，报告和给成员的材料只引用必要片段，特别留意请求头、Cookie 和转储中的敏感内容。

## 2. 复现并缩小场景

- 让检查在原条件下实际检出故障，保存首次失败的证据，并确认命中用户描述的症状。能从原场景稳定复现后，一次去掉一个输入、配置或步骤，每次重跑，直到再移除条件会丢失同一症状，或记录仍无法拆分的条件。保存原场景供最终复验。
- 偶发故障用有界的重复触发、负载或时序调整提高复现率，记录触发次数、失败次数和观察区间。性能回退先固定版本、工作负载、环境和指标，测量可比较的基线，再用计时、分析器或可重复的版本二分定位。最终验收沿用项目要求的运行条件和时长。
- 进入原因验证前，要求有观察到的故障及能区分成败的反馈。无法复现或缩小到可检验场景时，继续能做的只读取证，报告已试的办法、证据能支持到哪一步和所缺条件。只有现有工具与材料不足时，才索取最少必要的脱敏样本、原环境访问或采样授权。已有可复核的复现或直接因果证据时可复用，并说明覆盖了哪一步。

## 3. 独立提出假设，按预测证伪

- 主持人把原始症状、已运行的复现和固定基线交给成员。成员独立从调用链、数据状态和反例等角度提出解释，说明依据，以及哪个可观察结果会支持或推翻各自的解释。成员独立提交后，主持人才把这些推断用于交叉质疑。
- 主持人合并重复解释，按证据和区分能力排序。复杂问题通常保留 3–5 个有实质区别的假设，每个写出“如果原因成立，改变某条件就应观察到什么”。探针运行前向用户简述排序、预测和拟做的对照，收到新线索就调整，按现有授权继续执行。
- 按圆桌的交叉质疑规则，把关键解释和探针的判定条件交另一名成员核查。优先用已有检查、断点或调试器，必要时在有区分能力的边界加临时日志，统一用本轮唯一的 `[DEBUG-任务标识]` 前缀。每次只改一个影响结论的条件，记录实际观察及假设的维持、修订、撤回或待核状态。
- 根因结论要解释原症状，并有受控对照或其他直接证据排除关键替代解释。若只观察到改动后症状消失，将修复表现与根因置信度分别报告。

## 4. 修复、清理与独立复验

1. 在授权范围内指定一名写入负责人。已有检查能覆盖真实触发链时直接复用，否则从最小复现提炼回归检查。在修复前运行并检出同一症状，修复后用同一检查确认通过。缺少合适的自动化入口时，复验实际触发路径，记录自动化覆盖缺口。
2. 保存必要的脱敏证据，搜索并清除本轮前缀对应的临时日志，按权限清理或归档临时探针。固定交付候选、配置和运行条件，在该候选上重跑**原始场景**与受影响的回归。偶发故障用与修复前可比的条件重复验证，报告实际失败次数与总次数。若验证后又有会改变结果的改动，定向复验受影响部分。
3. 由未参与实现的成员按[代码交叉审查](cross-review.md)核对最终候选与修复前后的原始证据，优先独立重跑关键检查。核实重要发现后完成获授权的修正，再复验受影响部分。独立复查受阻时按[缺员处理](../SKILL.md#用户参与及失败处理)推进其余工作，并如实报告缺口。
4. 交付时给出原症状、复现条件、核实的根因或尚待核的解释、前后结果、独立复查和余留缺口。若任务已授权提交或 PR，在说明中记录核实的原因。用户只要求定位时，交付定位证据和修复建议。
