# 项目交叉审查与修复复验

## 确定审查对象

核对实际目录、Git 根、分支、已有改动及项目规则。明确用户要求的是某个改动、功能链还是整个项目；没有 Git 的资料记录文件路径和版本依据，不为审查初始化仓库。

记录审查基线：适用的提交或比较范围、纳入的未提交文件、已知并行修改。必要时保存相关差异或文件摘要，勿输出密钥。文件变化后将受影响的结论标为需复验，重新核对差异；不要把旧证据用于新代码。

## 覆盖与分工

建立与范围相称的清单：`文件或业务路径｜负责视角｜已检查内容｜状态｜未检查原因`。状态可以是已检查、部分检查、未检查或明确跳过。多个成员有意重叠可以交叉核实，但不把重复阅读计成额外覆盖。

逐文件清单不能替代关键业务链核查。每个纳入范围的对象最终都有状态；不能执行的检查保留缺口。范围过大时明确本次完成的部分，不能把局部审查称为全项目验收。

给成员原始需求、验收条件、实际代码及必要上下文。需求视角检查漏做、误做和业务归属；实现视角追踪调用、数据流、异常边界；验证视角检查证据、复现条件和测试遗漏。按真实需要关注金额、权限、状态机、重复请求、失败重试和时间边界，不对每个小改动机械扩充审查。

## 发现与核实

发现至少包含：问题编号、位置、预期与实际、触发条件、影响、原始证据、已做和未做的验证。建议和纯风格偏好单独标明，不包装成 bug。

主持人合并同根因发现，保留来源，交给相关成员核查。收到反馈后先对照代码和业务规则，避免盲目修复误报。运行测试前确认连接目标和副作用；可用安全隔离环境时在该环境复现。静态证据充分但无法运行时，明确确认依据及运行验证缺口。

## 已授权修复

只审查时交付发现及修复建议。已授权审查并修复时：
1. 核实问题和修复范围，指定同一文件或紧密相关改动的负责人，保护其他工作。
2. 以最小改动修复根因，补充确能揭示错误的验证，复用已有有效用例。
3. 验证原问题和受影响路径；保留首次失败、未运行和受阻记录。运行基线用于区分原有失败与新增问题。
4. 由非实现者对照原始问题、实际差异与验证结果复查。新问题才触发额外检查，不机械重跑全部测试。

修复状态与问题成立状态分开。未经授权的远程操作、发布和生产写入不因讨论通过而发生。

## 最终报告

先给主要结论，再按影响排序列出已确认问题，附可核对位置与依据。分别回答：
- 需求是否符合；实现是否有真实错误；验证是否充分。
- 哪些问题已确认、待核或已否定；哪些修复已验证。
- 实际参与者与审查基线、已覆盖范围、未覆盖项及原因。
- 尚未解决的问题与下一步核对路径。

可以零发现；必须限定到已检查范围。不能把类型检查、mock 通过或文件已读替代真实主路径验证。
